# Tailscale H3 IP throughput: 95% WireGuard acceptance work

## Status

The 95% WAN acceptance target is **not passed**. This work is isolated from
Tailcat's source checkout, dependency references, and release branches. No
production VPN binary, node identity, route, firewall, or system tuning was
changed. The first diagnostic WAN comparison completed and cleaned up. A tool
request including the second candidate's build and remote test was blocked
before execution. The remote part was not retried through another route.
Subsequent local validation is recorded separately below.

## Initial WAN comparison

A denotes the one-vCPU host; B denotes the two-vCPU host. Same candidate binary,
Linux kernel TUN, inner TCP, MTU 1280, four application flows, 500 Mbps aggregate
offered ceiling, two 12-second samples per direction, no omitted warmup.
The baseline is this fork's standard native WireGuard mode with AWG disabled,
not a separately downloaded untouched official executable.

| Direction | WG round 1 | WG round 2 | H3 round 1 | H3 round 2 |
| --- | ---: | ---: | ---: | ---: |
| A to B | 343.88 | 244.65 | 173.27 | 191.19 |
| B to A | 203.27 | 220.67 | 246.40 | 254.40 |

Units are receiver-side Mbps. With only two observations, the statistical
median is their mean; it is not a completed three-round acceptance run.
A-to-B ratio is 0.61928; B-to-A ratio is 1.18131. The latter does not compensate
for the former. Baseline variability and the limited sample count preclude a
universal performance claim.

The diagnostic report returned passed=true for transport correctness and
cleanup_errors=[]. Its before/after production PID and active state matched.
These flags do NOT certify throughput parity.

## Concrete observation

During the first A-to-B H3 sample, A sent 222,717 IP packets but zero entered
its ready-batch API. In the opposite direction, B sent 311,111 IP packets,
310,910 of which entered 48,990 batch calls. This demonstrates an asymmetry in
how the existing TUN/send path presents work. It is evidence for investigating
producer/sender scheduling; it is not proof that this alone explains all of
the throughput gap.

## Changes

The isolated QUIC dependency adds an optional SendDatagramsWithPrefix API. It
preserves independent HTTP/QUIC DATAGRAM boundaries and copies caller-owned
payload before returning. Validation failures accept no packets. Partial
acceptance returns its exact count; callers never retry the accepted prefix.
The existing 32-frame send-queue bound and congestion/pacing rules remain.

The initial Tailscale integration retained already-ready TUN batches; the WAN
numbers above show that this alone did not solve the one-packet producer case.

The second integration sends H3 native-IP work through the existing bounded
peer queue and drains only work that is already available. It has no timer for
waiting to fill a batch. Old queued lifecycle stamps are checked before and
after connection establishment, so remove/re-add cannot revive stale data.
Exceptional MTU/fragmentation cases retain the existing packet path.

The new path is restricted to H3 native IP and requires the optional dependency
capability. Embedded reliable TCP stream mode is unchanged. Builds using older
published dependencies keep the existing path and report ip_batch_supported as
false, instead of claiming the batch implementation is active.

No change was made to Noise IK v2, live policy checks, TLS identity validation,
full-handshake refresh/hard-expiry intervals, browser role selection, congestion
controller defaults, or historical AWG profiles.

## Local validation of the second integration

- Nineteen related Tailscale Go packages passed their complete local suite with
  the candidate dependency; go vet passed for the H3 package.
- Real H3 batched data tests passed with ordinary and fragmented payloads,
  both directions, borrowed caller buffers and peer identity intact.
- A one-P scheduler model submits 128 separate packets and receives all of
  them through real H3. Five consecutive race-instrumented runs each used four
  batch enqueue calls. This is a deterministic local mechanism test, not WAN
  throughput or Linux kernel TUN performance.
- Targeted race tests cover queue bounds, partial close, local/peer generation
  invalidation, identity authentication, session lifetime, and KCI regressions.
- The new parity checker has threshold, missing-round, failure, profiling,
  unequal-limit, and rate-ceiling regression cases.

## Acceptance gate

scripts/verify-h3-wg-parity.py separates successful delivery from speed parity.
It requires complete, unprofiled, non-omitted, standard-WG/H3 kernel TCP samples,
the same offered limit, at least three distinct rounds for every direction and
flow count, and H3 median >= 0.95 * WG median in **every** comparison. A baseline
hitting the test rate ceiling is not accepted as proof of uncapped WG parity.
The current two-round WAN report is correctly rejected, including its slow
A-to-B direction. No target has been lowered to force a passing result.

## Delivery boundary

The second integration's WAN throughput, CPU cost, loaded latency, and sustained
behavior across full session refresh remain unmeasured. No release or dependency
release was made. Candidate builds use explicit local modfiles and must not be
presented as already published modules or production-accepted binaries.
